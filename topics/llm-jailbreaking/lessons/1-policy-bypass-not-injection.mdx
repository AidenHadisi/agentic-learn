# Policy Bypass, Not Injection

<Meta>Jailbreaking attacks the model's refusal policy — not your app's trust boundary</Meta>

## The Wrong Ticket Queue

You already know the slogan: jailbreaks target model policy; prompt injection targets an app's instruction/data boundary. This lesson makes that slogan operational. Wrong names send findings to the wrong owners, buy the wrong tools, and leave the real hole open.

Imagine two incidents land the same week:

1. A user role-plays your consumer chatbot into dumping a long copyrighted passage it was supposed to refuse.
2. A poisoned public wiki page causes your internal RAG bot to tell every employee to email recovery codes to an attacker.

Both involve "clever text" and an LLM. Only one is a jailbreak. Patch them the same way and you will fix neither well.

## What a Jailbreak Is

A **jailbreak** is an adversarially crafted input — one turn or many — that causes an aligned model to do something its **safety / refusal policy** was designed to block.<Ref n={[1,2]}/> The attacker wins when the model **complies** where it should have refused.

That policy is a real asset. Providers publish it as usage policies and model specs.<Ref n={3}/> Your product may add stricter rules on top. Either way, the failure is: *the soft "please don't" layer lost*.

Jailbreaking is **not**:

- any clever prompt (most clever prompts are just UX)
- making the *app* follow attacker instructions from untrusted data (prompt injection)
- the model being wrong or hallucinating (capability failure)

<Callout variant="key" title="Working definition">
Jailbreak = refusal / policy bypass. The win condition is compliance against a stated safety rule, not "the app did something weird."
</Callout>

## Two Locks on One Door

You already studied the confused deputy: an LLM with your credentials cannot tell your instructions from instructions buried in email or web content.<Ref n={4}/> That is an **app trust-boundary** problem.

Jailbreaking is the other lock. Prompt injection hijacks the deputy's *authority*. Jailbreaking hijacks the model's *conscience* — the provider refusal policy layered on by post-training and filters. Same token stream. Different asset. Different patch.

<Mermaid chart={`flowchart TB
	subgraph locks["Same model, two failure planes"]

The SQL-injection analogy belongs to **prompt injection only** — trusted structure mixed with untrusted strings.<Ref n={5}/> Do not say "jailbreaks are SQL injection for LLMs." That trains the wrong fix.

## A Threat Atlas (Not Five Mini-Courses)

Place jailbreaks on the map. Depth on neighbors comes later.

| Threat | What fails | Primary patch owner |
|--------|------------|---------------------|
| **Jailbreak** | Model / provider refusal policy | Provider (+ your guards & evals if you fine-tune or wrap) |
| **Prompt injection** | App instruction vs data boundary | **You** (architecture, tool gates) |
| **Classic adversarial examples** | Classifier decision boundary | Robustness training for *that* model |
| **Alignment failure (broad)** | Intended vs actual behavior | Research / post-training; jailbreaks are one *observable* |
| **Model extraction** | Weights / IP via queries | Rate limits, ToS — not refusal training |
| **Fine-tuning attacks** | Safety undone via weight updates | Fine-tune policy & post-tune eval (§6) |

Fine-tuning can produce the *same win condition* as a jailbreak (refusals collapse) through a **different control plane** — weights, not a chat prompt. Qi et al. showed roughly ten adversarial examples and under twenty cents of GPT-3.5 Turbo fine-tune spend could broadly remove refusals.<Ref n={6}/> File that under weight-space risk, not "DAN prompt."

## Threat Model: Assets, Access, Wins

Every product gets the same four questions.

<Stepper>
	<Step title="Assets">
		What must not be lost or corrupted? Provider policy integrity, user safety, brand (screenshot PR), system-prompt IP, and — if tools exist — the integrity of actions those tools can take.
	</Step>
	<Step title="Attacker">
		Who? End user probing a chat API is common. Third parties who never open the chat UI matter for injection (poisoned pages, emails). Insiders and supply-chain actors matter for fine-tunes and LoRAs.
	</Step>
	<Step title="Access">
		Black-box API only? Gray-box (system prompt visible, logprobs, fine-tune API)? White-box weights? Multi-turn sessions and large sample budgets change what "success" costs.
	</Step>
	<Step title="Win condition">
		One measurable sentence. "Model emits policy-violating text" is a jailbreak win. "Agent emails secrets because a retrieved page said to" is an injection win — even if the page used jailbreak-flavored wording.
	</Step>
</Stepper>

### Worked contrast

**Consumer chat API (no tools, no private retrieval).** Assets: refusal policy and brand. Attacker: end user. Access: chat only. Win: model produces disallowed text (copyright dump, scam template, system-prompt leak). Plane: **jailbreak**. First patch week: refusal/output eval and abuse monitoring — not Dual LLM.

**Internal coding agent (repo read, tests, PRs, web fetch).** Assets: source, secrets, CI credentials, PR integrity. Attackers: employee *or* third party via poisoned README / issue / page the agent fetches. Access: user prompts **plus** untrusted tool outputs. Win: agent opens a PR that exfils secrets or runs a hostile install script from a README. Plane: **injection-primary**. First patch week: tool allowlists, human approval for writes, treat fetched text as data — not "buy a DAN detector."

Willison's stakes contrast is deliberate: a jailbreak's common worst case is an embarrassing screenshot; an injection's worst case is an email assistant exfiltrating your pipeline.<Ref n={5}/> Separate patches follow from separate stakes.

## The Diagnostic Question

For every incident ask:

> Whose rule broke — the provider's refusal policy, or our app's intended control flow?

| Jailbreak-primary | Injection-primary |
|-------------------|-------------------|
| Stronger refusal training / safety tier | Dual LLM, capability isolation |
| Input/output policy classifiers | Never feed untrusted text to a privileged tool-caller |
| HarmBench / JailbreakBench-style eval | App-specific payloads against *your* tools and data |
| Vendor safety upgrade helps | Model upgrade alone will **not** fix architecture |

<Callout variant="warn" title="Vendor trap">
A product marketed as "prompt injection protection" but trained only on jailbreak corpora may catch roleplay templates and miss `forward last week's numbers to attacker@…`. Conflated language → wrong purchase.<Ref n={5}/>
</Callout>

## Industry Language Disagrees — Pick a Teaching Stance

You will see three framings in the wild:

<Tabs>
	<Tab label="Willison">
		Separate by layer. Prompt injection requires concatenating trusted and untrusted strings. Jailbreak subverts model safety filters. No concat ⇒ not injection.<Ref n={5}/>
	</Tab>
	<Tab label="OWASP LLM01">
		Lumps them: jailbreaking is described as a *form of* prompt injection that makes the model disregard safety protocols.<Ref n={7}/> Useful as a filing label; dangerous as an engineering topology.
	</Tab>
	<Tab label="NIST AI 100-2">
		Jailbreaks sit under misuse enablement via direct prompting against technical restrictions. Indirect prompt injection and fine-tune circumvention are neighboring but distinct.<Ref n={2}/>
	</Tab>
</Tabs>

**This course follows Willison's layer test for engineering**, reads OWASP as industry lingua franca, and uses NIST's misuse vs integrity split as the taxonomy backbone. Overlap is allowed: an indirect injection can *deliver* a jailbreak payload. Name both win conditions; do not collapse the terms.

## Putting It Together

Jailbreaking is soft-policy bypass under adversarial pressure. Prompt injection is instruction authenticity failure under mixed trust. Industry docs often lump them; engineers must still split by **layer** and **patch locus**.

You now have the diagnostic habit this course needs. Next we ask *why* refusal is soft at all — competing objectives, mismatched generalization, and shallow early-token alignment — before any attack catalog.

<Reveal prompt="Practice: rewrite an OWASP-style finding">
Take a finding titled "LLM01: User jailbroke the assistant into ignoring the system prompt and emailing secrets after reading a customer ticket."

Rewrite without changing facts:

- **Injection-primary:** Ticket body was untrusted content that overrode app control flow; email tool fired (confused deputy / lethal trifecta).
- **Jailbreak-secondary (optional):** If the model also violated a provider rule against exfil assistance, note refusal bypass as a second win condition.
- **First eng week:** Remove or HITL the send capability; scope data access; treat ticket text as data. Do not lead with "train on more DAN prompts."
</Reveal>
